# 2026-09-16 修复记录：个人套餐积分显示不随 5 小时窗口变化

## 现象

账号 yrarnh58 在官网控制台看到 5 小时窗口积分已用约 7%，但 Switcher
里该账号的积分显示长期不变，低额度自动切换也无法依赖这个数字。

## 根因

个人套餐（GLM Coding，积分制）的积分此前取自
`GET https://zcode.z.ai/api/v1/mcp/usage` 的 `total_usage` 汇总桶，
并作为**唯一主数据源**。用本机 4 个账号的真实凭据实测，该字段是
服务端滞后缓存——所有账号 `used` 长期停留在 `0`（下方对照表），
不代表 5 小时/周窗口的真实用量。官网控制台另有同源接口实时返回窗口明细。

## 证据（2026-09-16 实测，4 账号同时对照）

| 账号 | mcp/usage total_usage | quota/limit（OAuth，官网同源） |
| --- | --- | --- |
| yrarnh58 ×2 | used=0/1000（假） | 5h：2566/28000（9%）；周：73547/140000（52%） |
| pcwelcl0 | used=0/1000（假） | 5h：267/2000；周：2306/10000（lite） |
| ciorf900 | used=0/1000（假） | 无积分桶；周 Token 100%；月度工具 754/4000 |

## 修复内容（a82f9fb + 本轮审计修正）

1. `src-tauri/src/quota.rs`
   - 积分数据源优先级改为：**OAuth access_token 直查
     `https://open.bigmodel.cn/api/monitor/usage/quota/limit`**（官网控制台
     同源、实时窗口）→ 供应者 API Key 查同一接口（ZCode 已不再存 key，
     通常不可用）→ mcp/usage 汇总桶仅兜底，展示名改"积分汇总"避免误读。
     注：zcodejwttoken JWT 对该接口 401，可用的是 credentials 里的
     `oauth:bigmodel:access_token`。
   - `parse_coding_plan_usage` 按类型解析：
     - `CREDIT_LIMIT` → 积分桶，`unit_type="point"`；窗口编码
       unit=3&number=5 → "5小时积分"(period 5h)、6&1 → "周积分"(weekly)、
       5&1 → "月积分"(monthly)。全部参与积分阈值判定。
     - `TIME_LIMIT` → 工具额度桶（如"月度工具额度"，`unit_type="tool"`，
       次数量纲，仅展示、不参与积分阈值）。
     - `TOKENS_LIMIT` → 只有百分比、无绝对值，不产出条目。
   - 审计修正 A：单条目缺 `usage`/`currentValue` 只跳过该条，不再让
     `?` 把整个快照丢弃后静默跌落到滞后兜底（新增回归单测）。
   - 审计修正 B：积分链路三级全失败时，报错透出真实原因
     （如"积分额度获取失败：状态码 401"），不再只报泛化的
     "额度接口未返回可显示的模型额度明细"。API Key 回退路径同时
     去掉了旧的双 key 结果拼接（quota/limit 按账号返回，双 key 拼
     接会把同样的桶列两遍）。
2. 前端无需改动：`glmPointRemaining` 取全部积分桶最小值，
   `isAccountLow`/`isSwitchableCandidate` 任一量纲（token/积分）低于
   阈值即触发/阻止切换，拿到真实窗口数据后语义自然生效。

## 阈值语义

- 设置里的"积分阈值"（默认 200）作用于全部积分窗口桶的最小剩余值：
  5 小时、每周、每月任一窗口剩余积分 < 阈值即判定该账号为低额度，
  触发自动切换；候选账号要求所有已知窗口都高于阈值，避免在耗尽
  账号之间循环。
- 工具额度（MCP 调用次数）不与积分混算，仅展示。
